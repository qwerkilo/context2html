# 报告内联微调（组件互换）

日期：2026-10-30
状态：待实现
来源：grill-with-docs 会话，17 项决策

## Problem Statement

报告交付后，用户常常发现某个视觉组件不合适——柱状图看趋势不直观、卡片组比表格更适合这段内容、时间线选错了。今天唯一的补救办法是回到 agent，用文字描述不满意的地方，让 agent 重新生成整份报告。重新生成会改动其他已经满意的部分，而且一轮对话只能试一种方案。

用户要的是：拿到 HTML 之后，自己把某个组件换成另一种，改完保存，不用再找 agent。

## Solution

报告可以在生成时带上编辑能力。开启后，报告顶部出现「编辑」开关；进入编辑模式，每个可换组件被描边，点一下弹出候选组件列表（按当前数据过滤，同族优先），选中后原地换成新组件。换错了 Ctrl+Z 退回。改完点保存，浏览器下载一份新的 HTML，覆盖原文件即完成。

微调后的 HTML 就是最终源。之后要继续改，agent 读这个文件，不重新生成。

没有开启编辑能力的报告与今天完全一致：单文件、离线可开、关掉 JS 组件照样显示。

## User Stories

1. 作为报告作者，我想在交付后把柱状图换成折线图，以便让趋势读起来更准确。
2. 作为报告作者，我想把图表换成卡片组，以便内容更适合卡片式叙述。
3. 作为报告作者，我想把表格换成时间线，以便读者按时间顺序理解。
4. 作为报告作者，我想在换成完全不同类别的组件时看到数据如何映射，以便知道会丢什么。
5. 作为报告作者，我想在换之前看到映射预览并确认，以便避免误操作。
6. 作为报告作者，我想保留原始数据，以便换错了能换回原组件并完整恢复。
7. 作为报告作者，我想多步撤销，以便大胆尝试不同方案。
8. 作为报告作者，我想候选列表按我的数据过滤，以便不被喂不进当前数据的组件干扰。
9. 作为报告作者，我想同族候选排在前面，以便优先看到信息损失最小的选择。
10. 作为报告作者，我想知道哪些组件不支持替换，以便不去找不存在的按钮。
11. 作为报告作者，我想用顶部开关进入编辑模式，以便阅读时不会误触。
12. 作为报告作者，我想保存时下载一份新 HTML，以便像以前一样分享单个文件。
13. 作为报告作者，我想下载的文件仍然可编辑，以便做第二轮微调。
14. 作为报告作者，我想微调后的文件被 agent 当作源，以便后续修改不覆盖我的调整。
15. 作为报告读者，我想未开启编辑能力的报告和今天完全一致，以便阅读体验不被打扰。
16. 作为报告读者，我想报告离线打开、不需要服务器，以便邮件发一个文件就能看。
17. 作为报告读者，我想关掉 JS 也能看到组件内容，以便在受限环境里仍能阅读。
18. 作为报告读者，我想双语内容在换组件后仍然成对，以便语言切换不出错。
19. 作为技能维护者，我想校验器仍然能检查组件，以便质量门禁不因这次改动失效。
20. 作为技能维护者，我想新增一条检查：每个组件插槽必须有对应数据块，以便换组件不会产出空壳。
21. 作为技能维护者，我想 Python 与浏览器两套渲染器产出相同标记，以便生成与互换永不分歧。
22. 作为技能维护者，我想 14 个可换组件显式声明内容模型，以便增加第 15 个只是小改动。
23. 作为技能维护者，我想其余 17 个组件保持原样，以便这次改造不重写整个组件库。
24. 作为 agent，我想调用槽位接口一次拿到标记与数据块，以便不用手工维护两份副本。
25. 作为 agent，我想槽位接口拒绝与组件不匹配的数据，以便问题在生成时报错而不是在互换时暴露。
26. 作为 agent，我想报告里记录哪些位置是组件插槽，以便后续会话能找到它们。

## Implementation Decisions

**内容模型**。所有可换组件消费同一个归一化结构：标题、副标题、条目列表（标签、数值、备注、强调色）、系列列表（名称、数值数组）。组件读取自己需要的字段，忽略其余。这是跨族互换成立的前提。

**可换集合**。14 个数据型组件进入可换集合；Three.js、D3、PPT 质感、装饰性 SVG 等 17 个组件保持现状，不属于可换集合。集合的判定标准是「能否从内容模型渲染出有意义的结果」。

**组件插槽**。报告里每个可换组件是一个插槽，带稳定的槽位标识与组件标识。插槽同时持有渲染后的标记与它的内容模型数据。互换是插槽级操作，从不触碰周边正文。

**生成路径**。生成时仍把组件标记写死在 HTML 里，内容模型数据旁挂在文档内的一个 JSON 块里。不采用「加载时由 JS 渲染组件」的方案，因为那会让校验器看不到组件，也会让关掉 JS 的读者失去全部视觉内容。

**双渲染器与一致性**。生成侧（Python）与互换侧（浏览器 JS）各有一套渲染逻辑，两者必须从同一份数据产出相同标记。一致性由黄金用例锁定：每个可换组件一份固定数据，两边渲染后逐字节比对。

**槽位接口**。14 个可换组件由渲染器接口产出，接口接收组件标识与内容模型，一次返回标记与数据块。其余 17 个组件保持 agent 手抄代码的现状。

**编辑能力开关**。渲染器参数控制是否写入编辑能力标记；编辑器脚本只在检测到该标记时初始化。手动编辑模板也能打开，作为逃生口。

**运行时组件库**。14 个可换组件的渲染函数内联进报告，约 93 KB（原估 32 KB，实测偏大：编辑器核心与 DOM 接线都在内）。不做外链，单文件交付不被破坏。组件依赖的第三方库（仅 #26 需要 ECharts）按需加载：生成时若插槽里有 #26 就同步注入，没有就不注入；编辑模式下换到 #26 时才去取库。

**编辑界面**。顶部一个「编辑」开关进入编辑模式；进入后插槽描边可点，点击弹出候选列表。不采用悬停热区，长文档里容易误触。

**候选过滤与排序**。候选按槽位数据自动过滤：喂不进当前数据的组件不出现在列表里。同族判定以**当前组件的家族**为准，而不是数据的形状——一个只有条目的槽位若当前由 #4 条形图渲染，图表族仍排在前面，因为从图表换到图表的信息损失最小；只有当前组件未知时才回退到按数据形状判定。

**信息损失处理**。跨族互换前展示映射预览供确认；原始内容模型始终保留在数据块里，换回原组件即完整恢复。

**撤销**。改动记录为补丁列表，支持多步撤销。

**保存**。保存动作下载一份新的 HTML，内含更新后的标记与数据块。不需要服务器；`file://` 下同样可用。

**源的定义**。微调后的 HTML 是最终源。SKILL.md 需增加一条约定：用户提供已微调的报告时，以它为源继续编辑，不重新生成。

**不可换组件**。不属于可换集合的组件在编辑模式下不描边，悬停提示不支持替换。

**校验扩展**。新增一条硬检查：每个组件插槽必须有对应数据块。检查总数由 22 增至 23，文档中的计数需同步。

## Testing Decisions

**什么算好测试**。只测外部行为：给定内容模型，渲染出什么标记；给定报告，校验器给出什么结论。不测内部函数调用顺序、不测私有结构。

**槽位渲染器（Python）**。测每个可换组件：给定固定内容模型，输出包含期望的结构标记，且数据块可被解析回原内容模型。参照 `test_renderer.py` 的写法。

**两套渲染器一致性**。黄金用例：每个可换组件一份数据，Python 与 JS 各渲染一次，逐字节比对。这是本次唯一新增的测试接缝，也是防止两套实现漂移的唯一手段。JS 侧以纯函数方式在 node 下运行，不引入浏览器。

**校验器**。新增检查走现有 `run_all()` 接缝，参照 `test_validate_report.py` 的既有写法：构造最小报告，断言通过；删掉数据块，断言失败。同时把新检查纳入 `mutation-smoke.py` 的变异体列表。

**编辑器 DOM 接线**。不做浏览器自动化。理由是渲染器已是纯函数、有黄金用例覆盖；剩下的只是事件绑定与开关显隐，用一份人工验收清单覆盖：进入编辑模式、换一个组件、撤销、保存后重新打开仍可编辑。

**不测**。不测下载动作本身（浏览器行为），不测 CSS 外观。

## Out of Scope

- 正文文字编辑（双语孪生会让中英不同步，文字交给 agent）
- 17 个非数据型组件的互换
- 服务器端原地保存
- 主题切换（已存在，不改）
- 导出 PPTX / PDF
- 编辑历史跨设备同步
- 组件内部参数微调（颜色、尺寸、间距）

## Further Notes

**两条 ADR 值得写**：
1. 生成时写死标记 + 数据旁挂，而不是加载时渲染——理由是校验与离线阅读优先于渲染器单一化。
2. 归一化内容模型，而不是逐对适配器——理由是适配器组合爆炸，而统一模型的损失可以用映射预览与可回退来补偿。

**分阶段建议**：内容模型与 14 个组件的渲染函数是地基，编辑器 UI 建立在其上；黄金用例与校验扩展随地基一起落地，否则后面每一步都缺护栏。

**规模提示**：这是多会话构建，不是一次会话能完成的工作。
